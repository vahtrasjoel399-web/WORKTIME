# Настройка писем-приглашений WorkTime

Функция создаёт сотрудника в Supabase Auth и `profiles`, а затем отправляет через Resend письмо с временными данными входа. При первом входе `force_password_change` направляет пользователя на обязательную замену пароля. Если почта временно недоступна, созданная учётная запись сохраняется, а администратор видит ошибку и может выпустить новый временный пароль и повторить отправку.

## 1. Создать аккаунт Resend

1. Откройте [resend.com](https://resend.com/) и зарегистрируйтесь.
2. Подтвердите адрес аккаунта и войдите в Dashboard.

## 2. Получить `RESEND_API_KEY`

1. В Resend откройте **API Keys** → **Create API Key**.
2. Назовите ключ, например `WorkTime Production`.
3. Выберите минимально необходимое разрешение **Sending access**. После добавления домена ограничьте ключ этим доменом.
4. Скопируйте значение `re_...` сразу после создания: повторно полный секрет не показывается.

Никогда не добавляйте ключ в Git и не используйте префикс `NEXT_PUBLIC_`.

## 3. Локальная разработка

В `apps/admin/.env.local` добавьте:

```dotenv
RESEND_API_KEY=re_your_key
EMAIL_FROM=WorkTime <onboarding@resend.dev>
NEXT_PUBLIC_APP_URL=http://localhost:3000
```

Для безопасной проверки доставки используйте поддерживаемый Resend тестовый получатель `delivered@resend.dev`; `bounced@resend.dev` имитирует bounce, а `complained@resend.dev` — жалобу на спам. Тестовый отправитель `onboarding@resend.dev` предназначен для разработки. Для писем реальным сотрудникам настройте собственный подтверждённый домен.

## 4. Переменные окружения в Vercel

Откройте проект WorkTime в Vercel → **Settings** → **Environment Variables** и добавьте для Production (при необходимости также Preview):

```dotenv
RESEND_API_KEY=re_your_production_key
EMAIL_FROM=WorkTime <noreply@YOUR_VERIFIED_DOMAIN>
NEXT_PUBLIC_APP_URL=https://worktime-one.vercel.app
```

В значениях не должно быть Markdown-ссылок, неразрывных пробелов или склеенных переменных. Каждая переменная добавляется отдельно.

## 5. Формат `EMAIL_FROM`

Поддерживаются:

```dotenv
EMAIL_FROM=WorkTime <noreply@worktime.ee>
```

или адрес без отображаемого имени:

```dotenv
EMAIL_FROM=noreply@worktime.ee
```

Значение `WorkTime noreply@example.com` неверно: при наличии имени адрес должен находиться в угловых скобках. Не указывайте `worktime.ee`, пока домен действительно не принадлежит вам и не получил статус Verified в Resend.

## 6. Подтвердить собственный домен

1. В Resend откройте **Domains** → **Add Domain**.
2. Добавьте домен, которым вы управляете (желательно отдельный почтовый поддомен).
3. У DNS-провайдера создайте ровно те DKIM/SPF записи, которые показывает Resend. Если доступен Domain Connect, записи можно добавить автоматически.
4. Вернитесь в Resend и нажмите **I've added the records / Verify**.
5. Дождитесь статуса **Verified**. DNS может обновляться не мгновенно.
6. Только после подтверждения установите `EMAIL_FROM=WorkTime <noreply@ваш-домен>` и при необходимости ограничьте API key этим доменом.

## 7. Повторно развернуть Vercel

После изменения переменных откройте **Deployments**, выберите последний production deployment → **Redeploy**. Переменные Vercel не применяются к уже завершённой сборке без нового deployment.

## 8. Отправить тестовое приглашение

1. Войдите в админ-панель как администратор.
2. Нажмите добавление пользователя.
3. Для тестового режима укажите `delivered@resend.dev`; для полного реального теста после верификации домена — доступный вам почтовый адрес.
4. Заполните имя, роль и временный пароль длиной 10–128 символов.
5. Создайте аккаунт. Модалка покажет, отправлено ли письмо.
6. Если отправка не удалась, исправьте конфигурацию, подождите минуту и используйте **Saada kutse uuesti**. На странице сотрудника повторная отправка задаёт новый временный пароль.

## 9. Проверить работу

1. В Resend откройте **Emails** и убедитесь, что письмо принято/доставлено.
2. Откройте письмо и проверьте CTA **Ava WorkTime**, HTML-вёрстку и текстовую fallback-версию.
3. Войдите временным паролем: любые защищённые URL должны перенаправлять на `/set-password?initial=1`.
4. Установите новый пароль и проверьте вход с ним повторно; старый временный пароль больше не должен работать.
5. Проверьте ошибочные сценарии: неверный email, дубликат, неверный временный пароль, повторную отправку чаще одного раза в минуту, удалённый профиль и запрос не от администратора.

Сервер пишет в лог только безопасный код ошибки, ID компании и сотрудника. Пароль, API key и auth token не логируются.

## 10. База данных

Новая миграция не требуется. Реализация использует существующие поля Supabase Auth `user_metadata.force_password_change` и существующую append-only таблицу `public.audit_logs` для статусов `employee.invitation_sent` / `employee.invitation_failed` и защиты от частых повторов. До запуска убедитесь, что текущие миграции проекта `0001–0020` уже применены.
